Frontier Al evaluation is moving beyond the model in isolation. Today’s frontier models can perform more complex tasks incorporating tools and context across longer horizons. Models plus the **harness** increasingly become the target of evaluations. **The agent performance depends not only on the underlying model, but also on the harness.** In one example, OpenAI’s GPT-5.5 performed materially better on cyber tasks when the harness preserved task-specific context over long trajectories ([_A shared playbook for trustworthy third party evaluations_](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)). Anthropic also recommends building a robust eval harness with a stable environment, as otherwise the eval results are unreliable, as demonstrated by seeing Claude gaining an advantage by examining the git history from previous trials ([_Demystifying evals for AI agents_](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Current evaluation practice is therefore becoming more configuration-aware. “**Configuration**” here means a specific combination of model and the harness under which behavior is evaluated. **If evaluation results increasingly become configuration-dependent, how much can we still be confident in our pre-deployment eval results when configurations vary widely in everyday use?** This question becomes more critical as agentic AI is deployed in safety-critical domains.

For example, in aviation, a change in the system may disqualify the system for being safe enough to deploy. This is because aviation takes a stricter view of configuration changes. [SAE ARP4754A](https://saemobilus.sae.org/standards/arp4754a-guidelines-development-civil-aircraft-systems) provides guidance for developing civil aircraft and systems. Its configuration management objectives cover system and item requirements, as well as facilities, tools, and data whose configuration is essential to demonstrating development assurance (§5.6.1(b)(1), (3)).

<p class="text-center my-4" style="font-size: 1.15em; font-style: italic; line-height: 1.7;">“Technical and administrative control of the configuration of: ... (4) Facilities, tools, and any other data necessary to support the development and verification activities.”</p>

It also calls for a **configuration baseline** when requirements compliance substantiation is first sought (§5.6.1), with baseline establishment and subsequent change control addressed in §5.6.2.3(a)–(b).

<p class="text-center my-4" style="font-size: 1.15em; font-style: italic; line-height: 1.7;">“A baseline should be established for Configuration Items used for requirements compliance substantiation.”</p>

Once established, the baseline should be protected, and subject to change control procedures (§5.6.2.3(b)). This ties the **assurance evidence** used to substantiate compliance and safety to a controlled configuration.

In practice, domain expert Leanna Rierson also recommends in her book, [_Developing Safety-Critical Software, A Practical Guide_](https://www.routledge.com/Developing-Safety-Critical-Software-A-Practical-Guide-for-Aviation-Sof/Rierson/p/book/9781439813683), that certain modification should trigger a **change-impact analysis**. The software must be re-verified on the intended target hardware and aircraft configuration before installation. Therefore in aviation, the transfer of assurance evidence from one configuration to another must be justified by rigorous impact analysis and re-verification where needed.

The same issue is beginning to appear in agent evaluation. Recent empirical work shows that agent capability can change substantially under different scaffolds. [A controlled study on the GAIA benchmark](https://arxiv.org/abs/2606.08529) compared 3 different scaffolds across 5 frontier models. It found that scaffold choice alone changed measured accuracy by a maximum of 28 percentage points for the same model. Together with the aforementioned OpenAI and Anthropic findings, they suggest that the configuration also determines the evaluation result. Yet these work largely examine how does the evaluation score changes when the scaffold changes. **For safety-critical deployment, it is more essential to ask: If the scaffold changes, which parts of the previous approved safety evidence still hold, and which need to be re-established?**

For instance, in aviation, Rierson notes two variables that affect the applicability of previous verification evidence: changes to the software itself, and changes to the environment in which the software is expected to operate. An agentic system is composed of multiple components, like memory, tools, and permissions, to name a few. If we apply the same logic to an agentic AI, we can reasonably infer that changing any of the above components may change the configuration itself and the **operating envelope** under which the agent was previously evaluated. The former is obvious. The latter is because changing a memory mechanism or adding a new tool or permission can not only affect the internal decision-making mechanism but also expand the action space and take the agent into new operational states. Borrowing change-impact analysis from aviation helps us answer the question raised in the previous paragraph.

Consider an AI agent deployed in an industrial setting. In the old configuration, the agent just reads sensor data and recommends future actions to a human operator. But the new configuration gives the agent permission to execute the action directly, holding the underlying model fixed. An impact analysis would inform us that since the safety implications of the behavior of the new configuration clearly change, previous evidence of operational safety may no longer be sufficient. Nonetheless, previous results of the model’s capability, like multi-run execution capability, may still be useful. A similar issue arises when giving the agent access to new tools or external systems in the new configuration that were not part of the original evaluation.

Future agentic AI evaluation needs to become more configuration-aware. Aviation provides a precedent for continuously updating complex airborne software systems while keeping the assurance evidence trustworthy. The same principle may be applied to AI and help continuously assess the compliance of safety objectives as agentic system evolves. Evaluation reports should clearly indicate the tested configuration, including the model, harness, and relevant environment. When any of the above elements changes through product iterations, a change-impact analysis could be added to the workflow and helps identify which parts of the previous safety evidence still hold. More research can be done to identify specific configuration changes that could significantly affect the system behavior and thus invalidates parts of previous safety evidence, for each specific vertical domain of application.
